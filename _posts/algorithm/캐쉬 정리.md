-	사용자 브라우저(HTTP 헤더) -> CDN(엣지 서버 전 서버 공유) -> in app local cache(서버 메모리)  -> 공유캐시 (redis 같은 인스턴스 간 분산환경)/ db buffer와 disk

-	캐시는 프론트에서 끝내주면 더 좋다. 서버 메모리 안 쓰기 때문. 

-	정적 이미지는 잘 안 변하지만, 장바구니는 몇 초마다 변경됨. 대상에 맞게 캐싱해야 함.

이미지는 몇 MB고 코드 목록은 해봐야 수 KB이므로 수 KB는 db에서 가져와도 되지만, 이미지는 프론트 단에서 캐싱.
주식 시세는 실시간이어야 하고, 공지사항은 5분은 지연되도 된다. 허용 TTL도 다르다는 의미. 

-	브라우저 캐시는 정적 리소스를 많이 올려둠. 재방문 시 계속 cache 사용. Cache-control, ETag, last-modified 같은 tag 사용. 정적 캐시를 업데이트하고 싶다면, 리소스를 해시 라던가 versioning 해서 값을 늘려줌. 
-	CDN은 전세계 유저에 공유되는 정적 리소스. Cache-contorl로 TTL 설정이나, cache purge함. CDN 콘솔/API로 직접 제어
-	In app cache는 서버 내부에 저장하는 로컬 캐시. 변경이 드물고 조회가 매우 잦은 데이터를 함. 국가 코드, 공통코드, 설정값 등. Spring의 caffeine 등이 있음. 네트워크 통신이 없고, latency 관점에서 빠름. 다만 로드밸런서에서는 동기화 문제가 있음.
-	공유 캐시는 redis 같은 것. 세션이나 장바구니, 사용자 별 상태는 로컬 캐시로 쓰면 안 됨. TTL과 evicition policy 등으로 만료를 설정. 각 서버들이 서로 동기화 통신을 하기에 in app 캐시보다는 느림.


-	실제 정적 리소스는 browser와 CDN. 전송 데이터가 크고 잘 안바뀌며 모든 사용자 공유
-	공지사항과 배너는 redis. 전송 데이터가 작고 잘 안바뀌며 모든 사용자 공유
-	권한 정보나 메뉴는 local cache와 redis 같이 씀. 변경이 드물고 전송 데이터가 작음.
-	국가 코드와 공통코드는 거의 변경이 없기 떄문에 local cache를 많이 이용.

브라우저 캐시의 태그
- browser의 요청이 있을 떄, 서버는 캐시 사용 여부- 만료기간- 재검증방법을 header에 넣어 return
- 브라우저는 서버의 정적 리소스를 로컬 사본에 저장(memory, disk 등)한 뒤에 사본을 재사용하는데, 신선도 체크를 함(재검증)
- 서버는 재검증 요청을 받았을 때, 갱신이 없다면 304를 반환하고, 바꼈으면 200 OK를 return

- Cache-control: 만료기간 확인. 조합해서 사용 가능
    - public : 개인의 브라우저만이 아니라 CDN에도
    - private : 브라우저에만
    - no-store : 절대 저장 금지
    - no-cache : 저장 하고 항상 재검증
    - must-revalidate : 만료되면 재검증(CDN이 유저를 위해 웹 서버등에서 재검증 실패했어도 과거 이미지를 return하기도 하는데, 이러한 행위 금지)
    - immutable : 재검증 X
ETag- if-none-matchs : 재검증 기준이고 가장 우선순위 높음
last-modified - if-modified-since: 재검증 기준

특히 인덱스 페이지는 no-cache, no-store, must-revalidate로 안전장치를 걸어놓는 경우가 많음. 자주 바뀌기 때문. 


web server단에서 보통 들어있음.
```
server {
    listen 80;
    server_name example.com;

    # Global default: Do not cache dynamic API data by default
    location /api/ {
        add_header Cache-Control "no-store, no-cache, must-revalidate";
    }

    # Global asset override: Cache static assets aggressively
    location ~* \.(jpg|jpeg|png|gif|css|js)$ {
        add_header Cache-Control "public, max-age=31536000, immutable";
    }
}
```

replication lag는 어떻게 해결했냐? 
(data sync between master - slave )
    - Read-Your-Own-Writes Consistency: update 이후의 read는 master에, 안 중요한 read는 slave에
    - When a user updates data (e.g., changes their profile picture), route their immediate subsequent read requests strictly to the Primary database for a short window (e.g., 5 seconds). Send generic, non-urgent reads (e.g., viewing other profiles) to the replicas.
    - Use Caching as a Buffer: update 이후에 즉시 redis에 저장해서 한동안 redis return
    - Write updates to both the primary database and a fast in-memory cache (like Redis). Direct immediate application reads to the cache. This gives the replica database breathing room to catch up in the background without the user noticing.
    - rack Replication Lag Logically: replica에 문제가 있는 지 검사하고 문제있으면 다른 곳으로 돌리기 
    - Use replication lag checkers or GTID (Global Transaction Identifiers). If the application detects a replica's lag is above a certain threshold (e.g., > 1 second), temporarily stop routing traffic to that replica and fall back to the primary or a healthier replica.
    - Eliminate Long-Running Read Queries on Replicas: replica에서 오래 걸리는 query가 실행되고 있다면 이는 장시간 전용 query 적합한 snowflake등에 맡기기
    - If a replica is busy processing an expensive, unindexed analytical query for a user, it may block or delay the replication thread from applying new updates. Offload heavy data science reporting to a dedicated data warehouse (like BigQuery or Snowflake) instead of your live read replicas.

- Write-Through CacheWhen your application issues a write request, the cache layer intercepts it, writes the data to the cache store, and immediately writes it to the backing database. The application only receives a "success" confirmation after both operations complete.
- When your application issues a write request, the data is written only to the cache. The application immediately receives a "success" confirmation. A background process later collects these updates and flushes them to the database in batches.

redis는 single thread인데 왜 빠른가? 
redis는 single thread여도 빠르게 설계되었다.
multi-thread여도 공유자원을 획득하기 위한 lock, context-switching, cache coherence 같은 문제가 들기 때문
redis는 왜 single thread를 선택했나?
redis는 CPU 병목이 문제가 아니었다, memory 대역폭과 network I/O의 병목이 사라지지는 않는다. 
multithread는 코딩이 어렵다.

1. redis는 in memory라서 disk IO가 없다 다만 서버 재시작 시 유실되어버리는데, 이는 RDB 스냇샷이나 AOF 로그로 보완하고 있다.
2. redis는 IO multiplexing을 한다. ready인 소켓만 골라 처리하기 때문에, 블로킹 없이 수만 커넥션을 관리한다.
이전의 IO는 blocking이었고, 10,000 커넥션이면 10,000 thread를 써서 메모리가 고갈되고 붕괴됐다.
이걸 non-blocking과 epoll기반의 IO multiplexing으로 메모리 효율을 극대화해 1개 서버로 10,000 커넥션을 쓸수있게 함
3. redis의 key 조회가 해쉬테이블을 사용하므로 시간복잡도 O(1)임. sorted set은 o(logn)임
4. RESP protocol. 길이를 먼저 알려주면 scan이 불필요. 구분자로 scan을 안함. 구분자 나올 때까지 한글자씩 scan을 하면 data 크기를 모르기에 buffer를 미리 할당불가능해 memory 낭비가 발생. redis는 buffer size 미리 확정가능. parsing 비용 극단적으로 줄일 수 있음.
5. pipeline과 batch write. 단 건도 있지만, 여러 개 명령 한꺼번에 전달도 가능. 명령을 하나씩 request 하고 response 하면 RTT(네트워크 왕복 시간)이 많이 추가되는데, 이를 극단적으로 줄임. RTT가 1ms라면 100 명령이면 100ms인데, 파이프라인으로 묶으면 1개로 1ms로 극단적으로 줄어듦.

redis도 multithread 지원을 함. background thread 추가해서 느린 삭제 작업은 main thread에서 안 하게변경. IO소켓 thread도 추가되어 network가 병목일 때 효과적으로 사용 가능. IO thread는 CPU 코어수보다 1-2개 작게 설정하는 게 추천. 서버가 8이면 6-7
이제 redis가 single thread라는 건, 명령 thread가 single thread라는 것. process 전체가 single thread는 아님. 

1. keys* 사용 : keys * 사용 하면 key scan이 o(n)이 되어버리고, n이 크면 main thread가 다른 요청 처리를 못함. 
2. 대형 hash/list 사용 : 거기다 그 하나하나의 key에 수십만 field가 있어 읽는게 느림
3. hot key 집중
